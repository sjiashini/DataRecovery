The weighted rating rises from 3.05 to 3.60. The biggest risks from the first review are closed: DNS rebinding, orphaned tools, an image resumed from the wrong disc, and work that couldn't be cancelled. The project now has version control, locked dependencies and 150 tests. What holds it below 4 is delivery automation (no CI, no build gate), missing data housekeeping (event retention, schema versions) and the 2,545-line single-file frontend. None of the fixes has yet been exercised on a real failing disc or pen drive.

What changed since the first review

Fixes in this round

Security and data safety

  • Host and Origin checks block DNS rebinding, so the token page is no longer served to foreign host names.
  • MEDIA_ROOTS enforced on inputs. Root checks resolve junctions and symlinks, and outputs must sit strictly inside a root.
  • Each image records its source drive. Resuming from a different disc is refused.
  • A per-image lock means only one tool works on an image at a time.
  • Media outputs can't replace recovered files, and can't land in the folder of the recovery that is running.
  • Quoted paths and the legacy route's unchecked conversion are fixed.

Reliability and delivery

  • A startup reaper stops orphaned tools, and shutdown stops running tools safely.
  • Cancel requests made just before a tool starts are no longer lost.
  • Cut, join and transcode are cancellable jobs. Separate RECOVERY and ENCODER locks let imaging and transcoding overlap.
  • The real ddrescue run now uses the sector size it shows.
  • Git with a GitHub remote, hash-locked dependencies, a folder exe build without .env, and a one-step setup script.
  • scripts/check.py, CLAUDE.md, two skills and a reviewer agent. Tests grew from 82 to 150.

Detailed analysis

Where each dimension stands now

01

Architectural style

3.5 → 4.0
Improved
The four root modules now live inside vs_app, which has one sub-package per layer. core/ has no I/O, since the token file moved to storage/. Recovery, repair and media all run as jobs through one launcher, and the locks are named after the resources they protect.
Remaining
The legacy /api/ddrescue and /api/photorec routes still run tools inside the request. Repair and media run blocking code in threads, while recovery uses async subprocesses. There are still three UIs.
Why
Deleting the legacy routes is the cheapest step to a single execution path.
02

Scalability & performance

3.0 → 3.5
Improved
Splitting the RECOVERY and ENCODER locks lets a drive be imaged or carved while a video is transcoded. Media routes now wait on a job instead of holding a worker thread.
Remaining
Each log event is still its own SQLite commit. Uploads still write with blocking calls inside the async handler. A transcode and an imaging run now share disk and CPU, which may slow imaging on a failing disc.
Why
These limits only show under heavy use, which is rare for one user.
03

Reliability & resilience

3.5 → 4.0
Improved
Orphaned tools are reaped at startup. Each image has a lock held by the kernel, so no stale lock can be left behind. Images record which drive made them, and a resume from a different one is refused. Cancel can no longer be lost before a tool starts, shutdown stops tools with SIGINT, and Share/Release are blocked during imaging.
Remaining
Storage write failures are only logged. Images made before today have no source record, so two pen drives of the same model and size can't be told apart for those. TestDisk still writes a stray testdisk.log into the backend's folder. None of this has been tested on a real failing disc.
Why
The safety logic is in place and unit-tested. One supervised real recovery would raise confidence from medium to high.
04

Security & compliance

3.0 → 4.0
Improved
Every request needs a loopback Host, and state-changing requests from another origin are refused; both were checked against a live server. Media inputs are sandboxed. Root checks resolve links and refuse the root folder itself. Quoted paths are handled the same everywhere. .env is never bundled into the exe.
Remaining
The CSP still allows inline scripts while the token sits in a page global, so any XSS would mean full API access. The rate limiter does nothing on loopback. The repository is public, so any future commit of personal data would be published.
Why
On a one-user machine the realistic attacker was a web page; that path is closed.
05

Data architecture

3.0 → 3.0
Improved
Each image now has a .source.json record, and the mapfile extent is used as a second identity check.
Remaining
The events table still grows without limit. There's no user_version or migration path, and persistence errors are still swallowed in the write pump.
Why
Low risk today. It becomes a real problem at the first schema change.
06

Integration & API design

3.0 → 3.5
Improved
Cut, join and transcode keep their old response shape and add a job_id. New /api/media_progress and /api/media_cancel endpoints exist, and busy messages name the resource that is in use.
Remaining
Routes are still named as verbs, policy errors still return HTTP 200 with success:false, the legacy routes are still there, and nothing is versioned.
Why
Fine for one in-repo client; it matters only if a second client appears.
07

Infrastructure & DevOps

1.5 → 3.0
Improved
The code is on GitHub. Dependencies are locked with hashes and work on Windows and Linux for Python 3.10+. The exe builds as a folder in a private environment from the lock. Setup is one re-runnable script, and scripts/check.py verifies a change in one command.
Remaining
There is no CI, although GitHub Actions is now possible. build_exe.bat doesn't run the checks before building. The exe is unsigned, which is acceptable for personal use.
Why
The biggest single gain of this round. CI is the last large step in this dimension.
08

Observability & operability

3.0 → 3.0
Improved
Media jobs appear in the same job history and event stream as recovery and repair.
Remaining
Log lines carry no job id, tool output is cut off mid-line, and there's no diagnostics export.
Why
When a long run fails, the log is still hard to tie to a job.
09

Maintainability & tech debt

3.0 → 3.5
Improved
Tests grew from 82 to 150 and now cover the HTTP guard, recovery and media routes, adapter cancel paths, locks and the client scripts. CLAUDE.md records the rules, and the README matches the code.
Remaining
The 2,545-line HTML file with inline JavaScript remains, and the browser UI has no tests. There are three UIs, and the mixed thread/async model remains.
Why
The riskiest code now has tests; the frontend is the main untested surface.
10

Technology fitness & lifecycle

3.5 → 3.5
Improved
Tools installed while the app runs are found without a restart, and the setup script detects and installs every external tool.
Remaining
The app is still tied to Windows 11, WSL2, usbipd-win and NVIDIA NVENC, customtkinter is barely maintained, and there is no cross-version test run.
Why
The platform tie is deliberate. Cross-version tests would come with CI.
11

Cost efficiency

4.5 → 4.5
Improved
Scripted setup and one-command checks reduce maintainer time.
Remaining
Nothing to pay. Code signing was skipped on purpose.
Why
Cost was never a constraint.

Prioritised roadmap

Next steps, in order

Quick wins · 0–3 months

  1. One supervised real recovery to validate the safety fixes
  2. GitHub Actions running the tests on push
  3. Build gate in build_exe.bat
  4. Delete the legacy single-tool routes
  5. TestDisk working folder fix

Mid-term · 3–9 months

  1. Event retention and schema migrations
  2. Surface persistence failures in the job
  3. Job ids on log lines; diagnostics export
  4. Upload writes off the event loop

Strategic · 9+ months

  1. Keep one UI and retire or freeze the others
  2. Split the page into files with a nonce-based CSP. Easier once there is one UI.
  3. Signed installer, only if the exe is shared
  4. Native Windows imaging for USB flash, to reduce the usbipd dependency

Assumptions and open questions

What would raise confidence

Assumed, as before: one user on one machine, a personal tool, and Windows 11 with WSL2 and an NVIDIA GPU as fixed requirements.

  1. Has a real recovery been run since the fixes? Reliability confidence stays medium until one has.
  2. Is the repo meant to stay public? If others will use it, CI, signing and an installer gain weight.
  3. Which UI should survive? That decision unlocks the frontend and maintainability work.
  4. How long are typical PhotoRec runs? That decides how urgent event retention is.
