System
CD/DVD and pen-drive recovery suite with video tools
Stack

Target scale
1 user, 1 machine, 1 device at a time
Reviewed
24 Oct 2026
3.1/5

The recovery path is well designed: it images the drive first and never writes to the source, ddrescue's mapfile lets interrupted runs resume, each stage has its own failure policy, and every external tool is launched as an argument list rather than through a shell. The weaknesses are around the code rather than in it: no version control or CI, a localhost boundary that a malicious web page could bypass, and reliability gaps in the paths outside the main recovery pipeline.

Update: three quick wins are fixed

After the review, three findings were fixed in the codebase. The test suite grew from 82 to 104 tests, and all of them pass.

  • DNS rebinding is blocked. Every request, including the page that carries the token, must have a loopback Host header. State-changing requests from a non-loopback Origin are refused. Checked against a live server instance: a rebound host now gets 403 and no token.
  • Media inputs are sandboxed. Cut, join, transcode and the repair reference must sit inside MEDIA_ROOTS. All root checks now resolve junctions and symlinks, so a link inside a root can't point outside it.
  • Orphaned tools are stopped at startup. ddrescue, PhotoRec or TestDisk left running inside WSL by a backend that crashed are stopped. They get SIGINT first so ddrescue saves its mapfile, then SIGTERM. Checked in WSL: a stray ddrescue was stopped and an unrelated process was left alone.

Executive summary

Strengths and risks

Top 3 strengths

  1. Data-safe recovery design. It always images first, keeps ddrescue's mapfile on cancel (SIGINT before SIGTERM), writes media outputs to temporary files and renames them into place, and never carves a partial image automatically.
  2. Clean layering. API, orchestration, execution and storage are separate. Each stage declares a failure policy (abort, continue, report), and every job ends in an explicit state.
  3. Defence in depth on inputs. Devices must match a pattern and appear in a live lsblk listing. Outputs must sit inside configured roots. Requests are validated with Pydantic, and the token comparison is constant-time.

Top 3 risks

  1. No version control, no CI. Versions are kept as folder copies, so there is no rollback, no change history and no automated test gate.
  2. DNS rebinding exposes the full API. There was no Host check, and the public page had the token embedded. Fixed
  3. Orphaned processes can corrupt an image. A ddrescue that outlives a crashed backend could share the image and mapfile with a new run. Fixed

Detailed analysis

What works, what doesn't, and why it matters

01

Architectural style

3.5 / 5
Works
The layers in vs_app/ are real. Pipeline.run applies the per-stage policy in one place, the adapters wrap each tool's process handling and parsing, and recovery_core.py holds pure policy logic shared with the desktop GUI.
Doesn't
Recovery uses async subprocess adapters while repair and media use blocking Popen in threads. The /api/ddrescue and /api/photorec routes skip the job system entirely, with no pidfile and no cancellation. Four modules live at the project root, so imports only work from there. There are three UIs.
Why
At this size the duplication is survivable, but every feature has to be added on two paths, and the bypass routes undo the safety guarantees the README advertises.
02

Scalability & performance

3.0 / 5
Works
Horizontal scale isn't needed. Streams are parsed line by line or in 64 KB chunks, state events are throttled to every 0.5 s, and saves are combined about once a second.
Doesn't
One lock covers all recovery and media work, so you can't trim a video during a multi-hour imaging run. Every log event is its own commit. Cut, join and transcode hold an HTTP request and a worker thread for their whole run. Uploads write with blocking calls inside an async handler.
Why
These hit how the app feels to use, which matters more than raw throughput for a desktop tool. The README's 280 fps NVENC figure isn't backed by a benchmark in the repo.
03

Reliability & resilience

3.5 / 5
Works
Image-first with mapfile resume, jobs a crash left running are closed on restart, outputs are written to temp files, leaked WSL keepers are cleaned up, and TestDisk has a 120 s timeout.
Doesn't
Tool processes weren't reaped after a crash (now fixed), and nothing stops two runs on one image. Media jobs can't be cancelled because the routes never pass a cancel check. Persistence failures are only logged. The bash -lc login shell loads profile scripts, so tool behaviour can drift.
Why
The product promises not to lose data. The main path keeps that promise; the side paths don't.
04

Security & compliance

3.0 / 5
Works
A 256-bit token per launch compared in constant time, loopback bind, no CORS, CSP and anti-framing headers, argument lists only, bus IDs validated before they reach PowerShell, and escaped page output.
Doesn't
No Host or Origin check while the public page carried the token (fixed). MEDIA_ROOTS wasn't enforced on inputs, and root checks didn't follow links (fixed). The build bundles .env into the exe. CSP allows inline scripts while the token sits in a global. The per-IP rate limiter means nothing on loopback.
Why
On a single-user machine, the threat that matters is a web page reaching the loopback server. Recovered files may contain other people's personal data; whether a retention policy applies is an open question.
05

Data architecture

3.0 / 5
Works
SQLite in WAL mode with a primary key per job, an index on kind and created time, and a (job_id, seq) key that makes event replay deterministic.
Doesn't
The events table grows without limit, there's no schema version or migration path, the job's truth lives both in memory and in the database, and the in-memory job index is never pruned.
Why
Low risk today. It will cause trouble at the first schema change or after months of chatty PhotoRec runs.
06

Integration & API design

3.0 / 5
Works
Starting a job returns a job id and an events URL; the event stream supports replay and a 15 s heartbeat, with polling as a fallback. OpenAPI is turned off, which is sensible on loopback.
Doesn't
Route names are verbs, policy errors return HTTP 200 with success:false while validation errors return 422, a GET opens a native file dialog, and there's no contract for the companion script.
Why
Fine for one in-repo client; brittle as soon as a second client depends on it.
07

Infrastructure & DevOps

1.5 / 5
Works
Top-level dependencies are pinned, the PyInstaller spec is reproducible, and the runtime folder can be relocated.
Doesn't
No git, versions kept as folder copies, stray artefacts in the project root, no CI, linter or type checker, indirect dependencies unpinned, WSL setup done by hand, and an unsigned one-file exe that antivirus tools often flag.
Why
This drags the overall score down the most. One bad edit can't be rolled back.
08

Observability & operability

3.0 / 5
Works
Rotating file log (5 MB × 5), a saved event stream per job, a live stage timeline, tool and status probes, and a 30 s progress summary in the job log.
Doesn't
Logs are free text with no job id, tool output gets cut off mid-message, and there's no diagnostics export. Metrics and tracing aren't needed at this scale.
Why
When a multi-hour run fails, the log is the only evidence of what happened.
09

Maintainability & tech debt

3.0 / 5
Works
Fast tests cover parsers, policy, the job state machine, the store, the pipeline and media argument building. Modules are small and the docs are extensive.
Doesn't
No tests for routes, adapters, flows or the frontend (the HTTP guard now has tests). The page is one 2,545-line HTML file with inline JavaScript. The README references a missing guide and claimed protections the code didn't have. Some helpers are duplicated across modules.
Why
The code most likely to break, the process plumbing, has no tests.
10

Technology fitness & lifecycle

3.5 / 5
Works
ddrescue, PhotoRec and TestDisk are the standard tools for this job. Python, FastAPI and SQLite are easy to hire for. Running Linux block tools through WSL is pragmatic on Windows.
Doesn't
Tied to Windows 11, WSL2, usbipd-win and NVIDIA NVENC. usbipd's CLI has already changed under the code. customtkinter is barely maintained. The README says Python 3.10+, but this machine runs 3.14 and nothing tests across versions.
Why
Every link in the platform chain can break on an update the app doesn't control.
11

Cost efficiency

4.5 / 5
Works
No licences to pay and no cloud bill. GPL tools (HandBrake, ffmpeg) run as separate programs and aren't bundled.
Doesn't
Total cost comes down to setup friction (WSL, usbipd, drivers, apt packages) and one maintainer's time.
Why
Scripting the setup is the cheapest way to lower that cost.

Prioritised roadmap

What to do, in order

Quick wins · 0–3 months

  1. Put the project under git and move stray artefacts. Needed before everything else.
  2. Host and Origin checks in the API guard
  3. Enforce MEDIA_ROOTS; resolve links
  4. Reap orphaned tools at startup
  5. Add a per-image lock
  6. Drop .env from the build; lock dependencies with hashes
  7. Delete the legacy single-tool routes
  8. Minimal CI: lint and tests on push. Needs git.

Mid-term · 3–9 months

  1. Move media work onto the job manager. Needs CI.
  2. Split the global lock. Needs step 1.
  3. Route and adapter tests with fake processes
  4. Event retention and schema migrations
  5. WSL setup script; missing-tool report
  6. Job ids on log lines; diagnostics export

Strategic · 9+ months

  1. Keep one UI and retire or freeze the others
  2. Move root modules into the package with a pyproject.toml
  3. Split the page into files with a nonce-based CSP
  4. Signed installer instead of the unsigned exe
  5. Evaluate native Windows imaging for USB flash to reduce the usbipd dependency. Needs step 2.

Assumptions and open questions

What would raise confidence

Assumed: one user on one machine, a personal or small-team desktop tool, and Windows 11 with WSL2 and an NVIDIA GPU as fixed requirements.

  1. Who uses it? Distributing the exe raises the stakes on signing, installers and update channels.
  2. Which browser? Local-network protections vary by browser, which changed how exposed the rebinding gap was.
  3. Has the 280 fps NVENC figure been measured on this hardware?
  4. Are the sibling folders older versions of this project, or separate products that share code? That decides how to build the git history.
  5. Do recovered files contain other people's personal data? If so, retention and handling may be a compliance concern.
  6. How long are typical PhotoRec runs, and how many log lines do they produce? That decides whether per-event commits matter.
  7. Should the desktop GUI and the companion script stay supported? The answer sets how much to consolidate.
Based on the source code in VideoStudio-V3 (about 5,000 lines of Python plus the web page) and test runs on 24 Oct 2026. Every score cites evidence from the code; where evidence was missing, the question is listed above instead of a guess.
