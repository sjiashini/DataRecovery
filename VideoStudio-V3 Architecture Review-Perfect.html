Detailed analysis

Where each dimension stands after phase 1

01

Architectural style

4.0 → 4.5
Improved
The legacy routes ran ddrescue and PhotoRec inside the HTTP request, outside the job system, with no cancel. They're gone, so every recovery tool now runs as a job.
Remaining
system.py still starts two subprocesses itself: the tool probe and the TestDisk window. Repair and media still run blocking code in threads, while recovery uses async subprocesses. There are still three UIs.
To reach 5
Move those two calls into execution/, use one execution model for long work, and keep one UI.
02

Scalability & performance

3.5 → 3.5
Improved
Nothing targeted in phase 1.
Remaining
One SQLite commit per event, blocking upload writes, no lower priority for a transcode during imaging, and the unverified "280 fps" claim.
To reach 5
Write event batches in one transaction, move upload writes off the event loop, lower the transcode's priority, and replace the claim with measured benchmarks.
03

Reliability & resilience

4.0 → 4.5
Improved
Imaging no longer starts when it can't finish: a 64 GB pen drive onto 20 GB of free space is refused up front instead of failing hours in. A full disk under .runtime now shows a warning in the job instead of silently stopping its history.
Remaining
No Resume button after a crash or cancel, no simulated failing disk in the tests, and no documented run on real failing media.
To reach 5
The device-mapper error test harness plus one supervised real-media run. Confidence stays medium until then.
04

Security & compliance

4.0 → 4.0
Improved
Two routes fewer. The old ones wrote images outside the job system's checks.
Remaining
The API token sits in the page's JavaScript, and the CSP allows inline scripts, so any XSS would mean full API access. No vulnerability scan in CI, and no fuzz tests for path tricks.
To reach 5
A session cookie scripts can't read (HttpOnly, SameSite=Strict), a nonce-based CSP, pip-audit in CI, and path fuzz tests.
05

Data architecture

3.0 → 4.0
Improved
PRAGMA user_version with a migrations table. A database from a newer version is refused instead of damaged. History is pruned to 200 finished jobs, events without a job are removed, and failed writes are visible.
Remaining
No PRAGMA quick_check at startup, no jobs.db backup, and tool versions aren't recorded in .source.json.
To reach 5
Those three, all small.
06

Integration & API design

3.5 → 3.5
Improved
The API is smaller and has a single path for each operation.
Remaining
Refusals still return HTTP 200 with success:false. There's no /api/v1 prefix and no typed responses or OpenAPI schema for the scripts that call it.
To reach 5
4xx and 409 status codes, /api/v1, and a published schema.
07

Infrastructure & DevOps

3.0 → 4.0
Improved
CI is green on run 40106605543 for main and 40106364129 for the branch. It covers Windows and Linux with Python 3.10 and 3.14, and every job lints and runs 163 tests. The build refuses to package failing code. Both workflows pass actionlint.
Remaining
No type checker, no pip-audit, and no automatic lock-update PRs. The release workflow hasn't run yet because no v* tag has been pushed. The 3 ffmpeg tests skip on GitHub's runners because they lack ffmpeg.
To reach 5
Add the two checks, automate lock updates, install ffmpeg in CI, and cut the first tagged release.
08

Observability & operability

3.0 → 3.5
Improved
A live test logged job=ad773fc2 … media job ad773fc2 started and … cancelled, so lines from one job can now be found together.
Remaining
No diagnostics export, no health endpoint that reports WSL and tool status, and tool output is still cut off mid-line.
To reach 5
A diagnostics button that zips the logs, job history, tool versions and drive list, plus a richer health endpoint.
09

Maintainability & tech debt

3.5 → 3.5
Improved
Tests grew from 150 to 163, and lint is enforced on every push.
Remaining
The page grew to 2,585 lines and has no browser tests. There's no coverage gate, no type hints and no decision records.
To reach 5
Split the page, add Playwright tests, add a type-check gate and a coverage minimum of around 85%, and write short decision records. That's phase 2 and phase 3 work.
10

Technology fitness & lifecycle

3.5 → 4.0
Improved
The support promise is now tested on every push, and the first run proved its worth by finding the 3.10/3.11 startup break.
Remaining
No WSL or usbipd version checks at startup, and customtkinter is still in use.
To reach 5
Startup compatibility warnings and retiring the desktop GUI.
11

Cost efficiency

4.5 → 4.5
Improved
CI is free on a public repository, and the automation saves maintainer time.
Remaining
Nothing material.
To reach 5
Comes with the release automation.

Assumptions and open questions

What would raise confidence

Assumed, as before: one user on one machine, a personal tool, and Windows 11 with WSL2 and an NVIDIA GPU as fixed requirements.

  1. Can a spare pen drive or scratched disc be used for a supervised run? It's the single biggest confidence gain left.
  2. Should the first release be tagged now? It would prove the release workflow end to end.
  3. Which UI should survive? That decision unlocks most of phase 3.
